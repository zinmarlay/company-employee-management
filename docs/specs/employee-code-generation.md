# Employee Code Generation Specification

## 1. Purpose

This specification documents the redesign of employee codes from user-entered
text to a server-generated, sequential, globally unique, immutable business
identifier. It is specification-only and does not implement PHP, migrations,
seed changes, or tests.

The design must extend the existing Pure PHP, SSR, PDO, custom-router,
migration-runner, lazy-connection, and localization architecture.

## 2. Current behavior and problem

The current EmployeeInput DTO contains employeeCode. The validator requires and
trims employee_code, the service performs employee-code uniqueness checks, and
the PDO repository inserts and updates the submitted value. The employee
create/edit form exposes an editable employee-code field.

This permits arbitrary user-selected codes and permits an edit request to
change an existing code. Current development data uses EMP001 through EMP004,
but there is no server-owned allocation or immutable-code rule.

## 3. Final business rules

- Employee code is generated by the server during creation.
- Users never manually enter or edit employee_code.
- A request-supplied employee_code cannot override or replace a generated code.
- Codes are globally unique, sequential, and immutable after creation.
- Deactivation does not release or reuse a code.
- employees.id remains the internal primary key and is not the business code.
- The valid range is 1 through 999999.
- Existing branch, department, email, employee type, hire date, status, and
  dispatch rules remain unchanged.

## 4. Employee-code format

The canonical format is:

    ^EMP[0-9]{6}$

The code is EMP followed by exactly six ASCII digits. The valid range is
EMP000001 through EMP999999.

Canonical examples:

- EMP000001
- EMP000002
- EMP000003
- EMP000004
- EMP999999

The implementation must not use employees.id directly, uppercase user input,
reuse codes, add separators, or generate EMP1000000.

## 5. Create behavior

The create form displays:

English: Employee Code / Automatically assigned

Japanese: 社員番号 / 自動採番されます

It contains no editable employee_code input and no hidden employee_code
authority field.

The request flow is:

    POST /employees
      -> EmployeeController::store()
      -> validate user-editable fields
      -> EmployeeService::createEmployee()
      -> validate business relationships
      -> allocate a code in the persistence transaction
      -> insert the employee
      -> commit
      -> HTTP 303 redirect

The browser never generates the code. A malicious request containing
employee_code is ignored as an authority and cannot choose the inserted value.

## 6. Edit and immutability behavior

The edit screen displays the existing code as read-only or display-only text.
The update form does not submit employee_code as a mutable field.

The update repository SQL omits employee_code. If a caller posts an
employee_code field, the backend ignores it and preserves the stored value.
Readonly or disabled HTML is not the security boundary.

## 7. Server-side ownership

The server owns allocation, formatting, range checks, uniqueness protection,
persistence, immutability, and rollback. HTML is usability assistance only.
Direct requests and browser tampering must be unable to select or replace a
code.

## 8. DTO and input design

Remove employeeCode from the user-input DTO, or split create/update user-input
DTOs so neither accepts that field. Read models may continue to expose
employee_code.

The validator validates only editable fields: names, email, phone, position,
branch, department, employee type, and hire date. It does not require or
trust employee_code.

The repository insert operation receives validated user input and timestamps,
then obtains the code internally. The repository update operation receives
editable fields only and cannot change employee_code by its method contract.

## 9. Generation architecture

Add a minimal database-backed allocator:

- EmployeeCodeAllocatorInterface;
- a PDO allocator implementation using the same LazyPdoConnection as the
  employee write;
- a controlled sequence-exhaustion domain/application exception; and
- repository coordination that wraps allocation and employee insertion in one
  transaction.

EmployeeService coordinates the use case and validation. It must not contain
MAX-plus-one logic, raw locking SQL, or code-formatting logic. SQL and locks
remain in the persistence layer.

## 10. Sequence state

Add an InnoDB table conceptually named employee_code_sequences:

    sequence_name VARCHAR(64) PRIMARY KEY
    next_value INT UNSIGNED NOT NULL

Use one stable row named employee_code. next_value means the next unallocated
integer, not the last allocated integer.

The migration creates the table and initializes an empty database with
next_value = 1.

## 11. Exact allocation algorithm

1. Validate normal user fields before allocation where practical.
2. Begin a transaction on the employee-write PDO connection.
3. Select the employee_code sequence row using SELECT ... FOR UPDATE.
4. Fail with a controlled data-integrity error if the row is missing.
5. Read next_value as the candidate.
6. Reject candidates below 1 or above 999999.
7. Format EMP plus the candidate zero-padded to six digits.
8. Advance next_value by one with a prepared UPDATE.
9. Insert the employee using the generated code and validated fields.
10. Commit only after both sequence advancement and employee insertion succeed.
11. Roll back on every failure.

For candidate 999999, insert EMP999999 and advance state to 1000000. The next
attempt fails before generating or inserting another code.

Do not use SELECT MAX(employee_code) + 1. Do not calculate the next value only
in PHP without database coordination.

## 12. Transaction boundary and rollback

Sequence advancement and employee insertion share one transaction. A duplicate
email, foreign-key failure, unexpected exception, or any insert failure rolls
back both the employee row and the sequence increment.

The repository or a dedicated persistence transaction component owns
begin/commit/rollback. Controllers and views never manage transactions.
Nested transaction behavior must be explicit; the implementation must not
silently commit or roll back a transaction owned by another operation.

## 13. Concurrency behavior

The locked sequence row serializes allocations. Concurrent requests receive
different sequential values:

1. Request A locks the row and receives N.
2. Request B waits.
3. A inserts and commits.
4. B locks the row, receives N+1, inserts, and commits.

The existing employee-code UNIQUE constraint remains the final integrity
boundary for corruption or unexpected defects.

Integration testing should use two independent PDO connections against the
isolated test database where practical and verify distinct codes and correct
final sequence state.

## 14. Unique constraint

Keep employees.employee_code protected by
uq_employees_employee_code. The sequence table does not replace this
constraint.

Known duplicate-key failures continue through the existing
EmployeeDuplicateException conventions. A duplicate generated code indicates
sequence or data corruption rather than user format input; the transaction
rolls back and the application returns a controlled error.

Duplicate email behavior remains unchanged.

## 15. Sequence exhaustion and errors

EMP999999 is the final valid code. When next_value is 1000000 or otherwise
outside the range, creation fails before employee insertion. No number is
silently wrapped, reused, skipped, or expanded to seven digits.

Recommended user-facing key:

    validation.employee_code_unavailable

English:

    A new employee code is currently unavailable. Please contact an administrator.

Japanese:

    新しい社員番号を発行できません。管理者に連絡してください。

The message is shown through the existing form-level error behavior and never
exposes SQL, locking, or PDO details.

## 16. Migration strategy

A forward migration is required for employee_code_sequences. No migration is
needed merely for regex validation.

The migration must:

1. create the sequence table using existing InnoDB and charset conventions;
2. preserve the employee_code column and unique constraint;
3. preflight existing values and canonical target collisions;
4. convert approved legacy EMP001-style values to EMP000001-style values;
5. reject unsupported values or collisions before partial conversion; and
6. initialize next_value to the largest canonical suffix plus one, or 1 for an
   empty database.

If the largest suffix is 999999, initialize next_value to 1000000.

The migration must not delete rows, choose winners during collisions, or
silently rewrite arbitrary user-created codes. It must fail safely and require
explicit remediation for unsupported data.

Schema migration owns table creation and approved data transition. The
development seeder must not repair production data.

## 17. Existing-data transition

    EMP004

## 18. Development seeder behavior

The seeder uses EMP000001 through EMP000004 and does not reintroduce the
three-digit format.

It remains idempotent and non-destructive:

- insert missing known sample records;
- update only seed-owned matching records;
- preserve unrelated employees;
- never truncate or reset sequence state; and
- fail safely on identity conflicts.

After ensuring the four samples exist, development sequence next_value must be
at least 5 and must never be lowered. A higher value created by other
development data is preserved.

The seeder must work on empty, already-seeded, rerun, unrelated-data, and
post-rollback test databases. It is not a production-repair mechanism.

## 19. Repository responsibilities

EmployeeRepositoryInterface and PdoEmployeeRepository:

- persist validated editable fields with a trusted generated code;
- update editable fields without employee_code;
- read employee_code for list, detail, dispatch, and organization views;
- use prepared statements;
- coordinate allocator and insert on one PDO connection;
- own transaction rollback for allocation plus insert; and
- preserve existing duplicate exception behavior.

The repository must never treat browser employee_code as authoritative.

## 20. Service responsibilities

EmployeeService:

- validates editable input;
- performs existing branch, department, email, and other business checks;
- invokes creation without trusting employee_code;
- maps sequence exhaustion into the existing failure shape;
- preserves submitted editable values for ordinary validation errors; and
- invokes updates without a code field.

It does not parse, increment, generate, or update employee codes.

## 21. Controller responsibilities

EmployeeController handles HTTP status, form rendering, redirects, and request
mapping only. It does not generate a code, validate a code supplied by the
browser, put a code into a hidden authority field, or update a code directly.

## 22. View behavior

Create:

- show Employee Code and Automatically assigned, or their Japanese
  translations;
- do not render editable or hidden employee_code authority input.

Edit:

- show the existing generated code as display-only;
- do not submit it as an editable field.

List, detail, dispatch-company, dispatch-contract, and department views
continue displaying employee codes normally. Existing HTML escaping and SSR
submitted-value conventions remain mandatory.

## 24. Error handling

Ordinary invalid user input continues to return HTTP 422 with preserved
editable values and field errors.

Sequence exhaustion returns a controlled HTTP 422 or existing form-failure
response with a localized form-level error. No employee is inserted and the
sequence is unchanged.

Unexpected database failures use the existing exception boundary. Raw PDO,
SQL, and locking details are not shown to users.

A posted employee_code never results in a successful insert or update using
that posted value.

## 25. Security and data integrity

- The server owns all generated identifiers.
- DTO and repository contracts prevent mass assignment of employee_code.
- Update SQL omits employee_code.
- Allocation uses prepared statements and row locking.
- Allocation and insert share a transaction.
- Rollback restores sequence state.
- The UNIQUE constraint remains a final safeguard.
- ASCII formatting avoids ambiguous Unicode digit forms.
- Existing HtmlEscaper remains required for all displayed values.
- Codes are never reused after deactivation.

## 29. Acceptance criteria

1. Empty migrated database creation produces EMP000001.
2. Successful creates receive sequential six-digit codes.
3. EMP000004 is followed by EMP000005.
4. Create has no authoritative employee_code input.
5. Posted employee_code cannot override generated code.
6. Edit preserves the existing code, including under malicious input.
7. The existing unique constraint remains active.
8. Allocation uses a transaction and row locking, never MAX plus one.
9. Failed creation rolls back employee and sequence state.
10. EMP999999 is valid and EMP1000000 is never generated.
11. Exhaustion fails safely with no partial employee.
12. Seeder uses EMP000001 through EMP000004, is idempotent, preserves unrelated
    data, and never lowers sequence state.
13. English/Japanese UI and error text use the translator.
14. Migration and isolated integration tests cover transition, rollback,

15. Phase 08 search functionality is absent.

## A. Recommended architecture

Use one InnoDB employee_code_sequences row with next_value representing the
next unallocated integer. Remove employeeCode from user-input and update DTOs.
Use a PDO allocator and repository insert on the same LazyPdoConnection.
The repository owns the transaction; the service owns use-case validation;
the database owns locking and final uniqueness.

## B. Exact concurrency-safe algorithm

BEGIN; lock the employee_code sequence row with SELECT ... FOR UPDATE; read
next_value; reject values outside 1..999999; format EMP plus six padded
digits; increment next_value; insert employee; COMMIT. On any failure,
ROLLBACK. The row lock serializes concurrent allocations.

## C. Required migration and data-transition plan

Create the sequence table, preflight legacy values and collisions, convert only
approved EMP001-style records to six-digit records, preserve the employee
unique key, initialize next_value from the largest canonical suffix, and fail
safely for unsupported data. Keep production migration repair separate from
development seeding.

==================================================

1. # FINAL BUSINESS RULE

Employee Code is a SYSTEM-GENERATED business identifier.

Users must NOT manually enter employee_code.

Users must NOT modify employee_code after employee creation.

Format:

EMP + exactly 6 ASCII digits

Examples:

EMP000001
EMP000002
EMP000003
...
EMP999999

Properties:

- generated by the server
- sequential
- globally unique
- immutable after creation
- visible to users
- separate from the internal employees.id primary key

employees.id must remain the internal database primary key.

Do NOT use employees.id directly to generate or represent employee_code.

================================================== 2. CREATE BEHAVIOR
==================================================

The employee create form must not accept employee_code as user-editable input.

UI concept:

Japanese:

社員番号
自動採番されます

English:

Employee Code
Automatically assigned

When the user submits the employee create form:

POST /employees
↓
Controller
↓
Validate user-editable employee input
↓
EmployeeService
↓
Safely allocate next employee-code number
↓
Generate EMP000005
↓
Insert employee
↓
Commit transaction
↓
303 redirect

The browser must NOT generate the employee code.

A malicious/direct HTTP request containing employee_code must not be able to
choose or override the generated employee code.

Inspect the current request/DTO architecture and specify exactly how this
should be enforced.

================================================== 3. EDIT BEHAVIOR
==================================================

Employee Code is immutable.

The edit screen should display the existing code, for example:

社員番号
EMP000005

but the user must not be able to edit it.

The update application flow must preserve the employee's current code.

Even if a caller manually sends employee_code in POST /employees/{id}, it must
not change the persisted code.

Do not rely only on disabled/readonly HTML for this rule.

The backend must enforce immutability.

================================================== 4. SAFE SEQUENTIAL GENERATION
==================================================

Do NOT use:

SELECT MAX(employee_code) + 1

Do NOT calculate the next employee code only in PHP without database
coordination.

Those designs are unsafe under concurrent requests.

Inspect the existing PDO and transaction architecture and specify a
concurrency-safe solution appropriate for MySQL/MariaDB.

Preferred design:

A dedicated sequence table/state for employee codes.

For example conceptually:

## employee_code_sequences

sequence_name
next_value

or an equivalent minimal design consistent with this project.

Allocation must use a database transaction and safe locking/atomic behavior,
such as SELECT ... FOR UPDATE, where appropriate.

The specification must define the exact algorithm.

Example conceptual flow:

BEGIN

SELECT sequence state
FOR UPDATE

allocate current number

validate range

advance sequence

generate:
EMP + zero-padded 6-digit number

insert employee

COMMIT

If anything fails:

ROLLBACK

The specification must determine the best exact ordering based on the current
repository/service/transaction architecture.

================================================== 5. UNIQUE CONSTRAINT
==================================================

employees.employee_code must remain protected by a UNIQUE database constraint.

Sequence generation is the normal allocation mechanism.

The UNIQUE constraint remains the final integrity boundary.

Document how duplicate-key failures should be handled according to existing
project conventions.

================================================== 6. SEQUENCE EXHAUSTION
==================================================

Maximum valid code:

EMP999999

The system must never generate:

EMP1000000

When the sequence is exhausted, employee creation must fail safely with a
controlled application/domain error.

No employee should be partially created.

Document expected transaction behavior and user-facing handling.
